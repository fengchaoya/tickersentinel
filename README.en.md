# tickersentinel

English | [中文](README.md)

A market-watch and research assistant tailored to your own holdings, running continuously on your own computer. It stays quiet
and only speaks up when there is something you should know: when a stock moves sharply it pushes an alert right away, then searches
news, filings and the event calendar for the most likely cause; it sends scheduled briefs every day and, each evening, a digest of
upcoming earnings and macro events. Messages go to Feishu (Lark), and you can ask questions in Feishu or in a local web UI.
Holdings and sector linkages live entirely in config files — no industry or ticker is hard-coded.

> **Language note**: the program's push messages, web UI and CLI output are all in **Chinese**, and so are the design notes in
> [CLAUDE.md](CLAUDE.md). This README is the English guide to setting it up and running it.

- **Round-the-clock anomaly monitoring**: checks every 60 seconds by default and **pushes only on sharp moves** — no move, no message.
  US stocks are watched 24x5 (Sunday 20:00 to Friday 20:00 ET): pre-market, regular and after-hours use Yahoo minute bars; the
  20:00–04:00 overnight session uses prices of trade.xyz stock perpetuals on Hyperliquid. Foreign stocks follow their local trading
  hours; futures and crypto follow their own sessions. Several names in the same sector moving together are merged into one push,
  and each push ends with a macro snapshot (Treasury yields, crude, gold/silver, equity indices, VIX…).
- **Automatic attribution**: after an alert goes out, the LLM looks at news, SEC filings and calendar events around the move,
  first separating sector-driven from stock-specific, and posts its explanation as a reply under that alert. If there is no clear
  catalyst, it says so.
- **Scheduled briefs**: pre-market, after the close, and weekly.
- **Event calendar**: collects, up to 100 days ahead, earnings dates, insider proposed sales (Form 144), FOMC meetings, CPI / payrolls
  and other data releases, Treasury auctions, market holidays…; pushes a nightly digest and feeds the briefs and attributions.
- **Feishu push and chat**: pushes and threaded replies go through a Feishu bot (long connection, no public address needed). Message
  the bot to ask a question; it looks up macro data, intraday moves, news, alert history and the calendar before answering.
  Optional: sync the event calendar into a Feishu calendar and write every alert into a Feishu Bitable for labelling the true cause later.
- **Local web UI**: overview (chat, message feed, macro board), alert list and details, event calendar, macro trends page. Localhost
  only; can be installed as a standalone app from Chrome / Safari.
- **Local minute-bar store**: 1-minute bars for macro variables and holdings are saved every two minutes, so you are not limited by
  Yahoo keeping only about 30 days of 1-minute data.
- **Local LLM by default**: Qwen 27B in LM Studio — free, and your data stays on your machine; any task can be switched to Claude or
  OpenAI. Without an LLM everything still runs; briefs and attributions degrade to news lists.

Design details, the reasoning behind each decision and measured numbers are in [CLAUDE.md](CLAUDE.md) (development notes, long, in Chinese).

> **Disclaimer**: this project is for personal learning and research only and **is not investment advice**. Market data comes from
> free or unofficial sources (such as Yahoo Finance) and may be delayed, missing or wrong; attributions are generated by an LLM from
> retrieved news and may be inaccurate. You are solely responsible for any trading decisions you make.
> Please respect the terms of service and rate limits of every data source (Yahoo, SEC EDGAR, Hyperliquid, Feishu Open Platform, etc.).

## Quick start

No keys required: prices, news, filings and the macro calendar all have free sources. Requires Python ≥ 3.11 (3.12 recommended).

```bash
git clone https://github.com/fengchaoya/tickersentinel.git && cd tickersentinel
uv venv --python 3.12 && uv pip install -e ".[dev,web]"   # web: local web UI; add feishu if you want Feishu
cp .env.example .env               # runs fine empty; filling SEC_EDGAR_USER_AGENT and BLS_USER_AGENT (a contact email) is recommended
.venv/bin/tsen check               # check config, keys and every data source
.venv/bin/tsen replay --days 5     # replay the last 5 trading days of real minute data to see what would be pushed
.venv/bin/tsen run                 # run continuously; the web UI is at http://127.0.0.1:8765
```

The example config in the repo holds one optical-module stock (Lumentum, LITE) and uses the `console` push channel (prints to the
terminal and also writes to `data/outbox.log`). To use your own holdings and connect Feishu and a local LLM, see "Configuration" below.

- [uv](https://docs.astral.sh/uv/) downloads a suitable Python automatically (`brew install uv`, or `curl -LsSf https://astral.sh/uv/install.sh | sh`).
  Without uv: `python3 -m venv .venv && .venv/bin/pip install -e ".[dev,web]"`.
- There are four optional dependency groups: `web` (local web UI), `feishu` (Feishu push, chat, calendar / Bitable sync), `dev` (tests),
  `telegram` (not implemented yet). Without `web`, `tsen run` works normally, just without the web UI; without `feishu`, Feishu push
  falls back to printing in the terminal.
- **Install with `-e` inside the cloned directory**: the program locates the project directory (`config/`, `.env`, `data/`) from where the
  package lives, so you can run `tsen` from any directory. If the package is installed elsewhere, point the environment variable
  `TICKERSENTINEL_HOME` at the project directory (set it in the shell, not in `.env`: `.env` itself is looked up in the project directory).

## Configuration

### Three config locations

| File | What goes in it |
|---|---|
| `config/assets.yaml` | Holdings (plus watch-only assets that are not holdings), each one's news search terms and notes, alert sensitivity (defaults per asset class, overridable per asset) |
| `config/themes/<theme>.yaml` | Sector linkage, one file per sector: sector benchmark, peers, overnight signals, related companies, sector news queries, sector indicators. Shared by all holdings in that sector |
| `config/settings.yaml` | Settings not tied to any particular stock: time zone, brief times, detection frequency and cooldown, event calendar, base macro variables, data sources, LLMs, push channel, web UI, minute-bar store |

In the example, the active theme is "optical modules" (`optics.yaml`, referenced by LITE); "memory chips" (`memory.yaml`, with Seoul /
Tokyo overnight signals already set up) is a spare module that no holding references, so it is inactive. To try it, uncomment the MU
lines in `assets.yaml`. `tsen scope` shows the current monitoring scope on one screen.

Any misspelled field name is an immediate error (never silently ignored). Changes to `assets.yaml` and `themes/` are picked up by a
running `tsen run` within a minute, with a "监控范围已更新" (scope updated) push; changes to `settings.yaml` need a restart.

**Using your own holdings**: copy the whole `config/` to `config.local/` (already in `.gitignore`) and point the program at it. Your
holdings then never go public with git, pulls won't conflict with the example config, and `tsen scope add / tune` write there too.

```bash
cp .env.example .env                      # if you don't have a .env yet
cp -R config config.local
# then uncomment the TICKERSENTINEL_SETTINGS=config.local/settings.yaml line in .env
```

Which config is read: CLI `tsen --config path` > environment variable `TICKERSENTINEL_SETTINGS` (can be set in `.env`) > `config/settings.yaml`.
`assets.yaml` and `themes/` default to the same directory as settings.yaml; they can also be set separately with `TICKERSENTINEL_ASSETS` /
`TICKERSENTINEL_THEMES`. Relative paths in environment variables resolve against the project directory; relative paths given to
`--config` resolve against the current directory.

### Secrets: `.env`

Secrets and personal information go only in `.env` at the project root (not in git; `.env.example` is a blank template). Put the value
right after the equals sign. **Everything runs with none of them filled in**; the corresponding features are skipped or degraded:

| Variable | Purpose | If left empty |
|---|---|---|
| `SEC_EDGAR_USER_AGENT` | SEC requires contact info in the request header: "project name + your email" | A placeholder email is used; SEC may throttle or refuse |
| `BLS_USER_AGENT` | Request header for the US Bureau of Labor Statistics (BLS) release schedule, same format (can be identical to the SEC one) | No CPI, PPI, payrolls or JOLTS release times in the calendar; asked "is there a CPI next week?" the bot will say no. `tsen check` warns about this |
| `FEISHU_APP_ID` / `FEISHU_APP_SECRET` / `FEISHU_CHAT_ID` | Feishu push and chat (all three needed); calendar / Bitable sync needs only the first two | Pushes fall back to terminal printing; no asking from your phone |
| `FINNHUB_API_KEY` | Company news, earnings calendar (finnhub.io, free sign-up) | One fewer news source; earnings dates still come from yfinance |
| `ALPACA_API_KEY_ID` / `ALPACA_API_SECRET_KEY` | Price fallback (fills in when Yahoo fails or lacks a ticker) and official daily closes (alpaca.markets, free account) | Yahoo only, no fallback |
| `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` | Cloud LLMs; only called if selected in `llm.tasks` | Local model only |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`, `OPENDART_API_KEY` | Not implemented yet; leave empty | — |
| `TICKERSENTINEL_SETTINGS` | Optional, points to your own config (see above) | Reads `config/settings.yaml` |

### Commonly changed in `settings.yaml`

| Section | Default |
|---|---|
| `timezone` | Your local time zone (IANA name). The example says `America/New_York`; change it to yours first. It affects when briefs, event refreshes and the nightly digest run, what "tomorrow" means, times shown in pushes and the web UI, and the Feishu Bitable time zone. Anomaly detection follows each exchange's own calendar and is unaffected |
| `briefs` | Pre-market 07:30 (trading days only), 15 minutes after the close (moves earlier on early-close days), weekly on Saturday 09:00 (with a "linkage check-up" appended when there are suggestions) |
| `monitor` | Check every 60 seconds (`interval_seconds`); merge same-theme pushes for 10 minutes (`merge_minutes`, 0 = push each separately); 15-minute cooldown and other detection parameters under `monitor.price` |
| `events` | Refresh daily at 06:40 and 18:30, digest at 20:00; collect 100 days ahead (`lookahead_days`); macro calendar `events.macro`; manual entries `events.manual` |
| `macro` | Base macro variables `indicators` (see "Macro data" below) |
| `sources` | Primary price source yfinance, fallback Alpaca (`sources.prices`); overnight `sources.night.provider: hyperliquid` (`none` to disable); news sources |
| `llm` | LLM providers `providers` and which one each task uses, `tasks` (see below) |
| `notify` | Push channel `provider: console \| feishu`; `feishu_domain: feishu \| lark`; Feishu sync `feishu_sync` |
| `web` | `enabled`, `port: 8765`, `up_color: red` (red = up, green = down; `green` reverses it); `host` must be a loopback address |
| `bars` | Minute-bar store: collect every 120 seconds, backfill 29 days for new tickers, compress 1-minute bars older than 120 days into 5-minute bars |
| `storage` | Database paths (all under `data/` by default) |

Scheduled briefs are planned by local date and are currently designed for American time zones; in Asian / European time zones the
trading day a pre-market or close brief refers to may be shifted, so adjust the times yourself.

### Local LLM (LM Studio)

By default every LLM task (briefs, attribution, event digest, chat) uses `qwen/qwen3.8-27b` in LM Studio on your machine (4-bit, about 16 GB of memory).

1. Install [LM Studio](https://lmstudio.ai) and download this model from Discover (or `~/.lmstudio/bin/lms get qwen/qwen3.8-27b`).
2. **No need to start the server yourself**: before each call the program checks and, if needed, runs `lms server start` and `lms load`
   itself (context 32768, unloaded after 60 idle minutes). `lms` defaults to `~/.lmstudio/bin/lms` and need not be on PATH; if it lives
   elsewhere set `llm.providers.local.lmstudio.lms_path`, and if you don't want the program to manage LM Studio set `auto_start: false`.
3. "Thinking" mode is off (`reasoning_effort: none`): summarizing news needs no long reasoning, and this is several times faster.
   Measured on the author's machine (M5 Pro / 64 GB): about 15 seconds per attribution, about 40 seconds per brief, ten-odd to fifty
   seconds per chat answer.

- To change the model: edit `llm.providers.local.model`. For Ollama or another OpenAI-compatible service: change `base_url` and `model`
  and delete the `lmstudio` block.
- The local model cannot search the web; attribution relies only on the news and filings the program collects. To let Claude add web
  search: set `llm.tasks.attribution` to `[anthropic]` (Claude only) or `[local, anthropic]` (Claude only when local fails), and fill
  `ANTHROPIC_API_KEY` in `.env`.
- Each task can list several providers, tried in order; it degrades only when all fail.

### Push: Feishu

Pushes and replies go through a Feishu bot that receives messages over a long connection — **no public address or server needed**.
One-time setup takes about 15 minutes:

0. **Install the SDK**: `uv pip install -e ".[feishu]"`. For the international Lark, set `notify.feishu_domain` to `lark` (shared by push and calendar / Bitable sync).
1. **Create an app**: [Feishu Open Platform developer console](https://open.feishu.cn/app) (Lark: open.larksuite.com/app) → "Create custom app".
   You need to be in a Feishu organization / team where you have admin rights; if you don't have one, you can create a free team in the Feishu client.
2. **Enable the bot**: app details → "Add features" → "Bot".
3. **Get the credentials**: App ID and App Secret on the "Credentials & Basic Info" page go into `FEISHU_APP_ID` and `FEISHU_APP_SECRET` in `.env`.
4. **Grant permissions**: under "Permissions & Scopes" enable `im:message`, `im:message:send_as_bot`, `im:message.p2p_msg:readonly`
   (read direct messages users send to the bot) and `im:message.group_at_msg:readonly` (receive group messages that @ the bot).
5. **Open the long connection**: run `tsen feishu setup` in a terminal (needs only App ID and Secret); once it says it is connected
   ("已连接飞书"), **keep it running**.
6. **Subscribe to events**: "Events & Callbacks" → "Event configuration" → choose "Receive events through persistent connection" and save
   (the console checks the connection from step 5), then "Add event" → `im.message.receive_v1`.
7. **Publish**: "Version Management & Release" → create a version → set availability to yourself → submit for release.
   **Every later permission change only takes effect after publishing a new version.**
8. **Find the chat_id**: send the bot a message in Feishu (to use a group, add it to the group and @ it). The terminal from step 5 prints
   `FEISHU_CHAT_ID=oc_...`, and the bot replies with the same value. Put it in `.env`, then Ctrl+C. The "sender open_id" (`ou_...`) printed
   alongside is your own Feishu ID, which you may need for the calendar / Bitable setup.
9. **Verify**: `tsen feishu test` sends a test message and a reply threaded under it; `tsen check` shows the bot's name.
10. **Switch the channel**: `notify.provider: feishu` in `settings.yaml`. All pushes then go to this chat, and messages from other chats are ignored.
    If any of the three secrets is missing or the SDK isn't installed, it logs a single warning and falls back to terminal printing instead
    of crashing at startup; the "push channel" line of the startup message shows the channel actually in use.

### Feishu calendar and Bitable

Optional, off by default. Needs only `FEISHU_APP_ID` / `FEISHU_APP_SECRET`, regardless of whether Feishu is the push channel.

- **Event calendar → Feishu calendar**: earnings dates, proposed insider sales, lock-up expiries and macro events become Feishu events
  (30-minute events when there is an exact time, all-day events when there is only a date). Reschedules and confirmations update the
  same event; stale estimates are deleted; events older than `past_days` (7 days) are kept but no longer updated.
- **Alerts → Feishu Bitable**: one row per alert + attribution. The "label 真实原因" (true cause) and "notes 备注" (notes) columns are
  for you to fill in afterwards; the program pulls them back into `alerts.label / notes` in the database to evaluate attribution accuracy.

Both are created by the app under its own identity and then shared with you: you are a read-only member of the calendar (it mirrors the
event calendar, so edits made in Feishu are overwritten; to correct a date, use `events.manual`), and you get full access to the Bitable.

> This part has full offline tests (against a mocked Feishu API); the first time you set it up on real Feishu, watch the command output closely.

1. **Grant permissions**: enable `calendar:calendar` and `bitable:app` under "Permissions & Scopes", then **publish a new version**.
2. **Create the calendar**: `tsen feishu calendar-setup`. It finds your open_id, creates the calendar "tickersentinel · 事件日历", adds you
   as a member and syncs once. Then subscribe to it in Feishu Calendar (the "+" next to the calendar list → "Subscribe to calendar" → search
   for the calendar name; the app cannot subscribe on your behalf).
   If you'd rather not subscribe: set `notify.feishu_sync.invite_user: true` and events appear directly in your primary calendar as
   invitations (without notifications). Switching it back to `false` later does not remove events already added to your primary calendar.
3. **Create the Bitable**: `tsen feishu bitable-setup`. It creates "tickersentinel · 异动记录", prints the link and writes all existing alerts.
4. **Turn on the switches and restart**: `notify.feishu_sync.calendar: true`, `bitable: true`, then restart `tsen run`. From then on the
   calendar syncs after each event-calendar refresh; new alerts and freshly finished attributions are written to the Bitable in the
   background after each check; every 15 minutes everything is reconciled, and your labels are pulled back at most once an hour.
5. **Sync manually any time**: `tsen feishu sync`. Running it occasionally is fine, but don't keep it running alongside `tsen run` for long
   (e.g. in cron): the two processes will hit Feishu's concurrent-write conflicts.

Other options (all under `notify.feishu_sync`): `calendar_name`, `bitable_name`, `calendar_role` (`reader` | `writer`),
`event_minutes` (length of timed events, default 30), `past_days` (how far back to sync events, default 7).

- **Your open_id**: the setup commands look for it automatically in the `FEISHU_CHAT_ID` chat, but only use it when it's certainly you; in
  a group chat (several people have spoken or there are several members) they won't guess, since that could share the Bitable with someone
  else. In that case specify it with `--open-id ou_xxx`; it is remembered after the first time.
- **Label columns**: the program only updates the columns it generates. Empty cells in Feishu never overwrite labels already in the database
  (so a re-created empty column after a rename or deletion can't wipe your labels); don't rename columns; rows you delete are not written back.
- **On errors**: when permissions are missing, the command lists the ones to enable and links to the console. While running continuously,
  a sync failure never affects pushes or monitoring; the failing part isn't retried for 30 minutes, and each streak of failures produces only one reminder.

## Running

### Make `tsen` findable in your terminal

`tsen` is installed in the project's `.venv`, which a new terminal doesn't see by default. Pick one:

```bash
# one-time setup, works from any terminal afterwards (run inside the project directory)
mkdir -p ~/.local/bin && ln -sf "$PWD/.venv/bin/tsen" ~/.local/bin/tsen
echo $PATH | tr ':' '\n' | grep -x "$HOME/.local/bin" || echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc

# or activate the virtual environment each time
source .venv/bin/activate

# or use the full path
.venv/bin/tsen check
```

`tsen` = `tickersentinel` = `python -m tickersentinel`. All command output and push messages are in Chinese.

### Running continuously

```bash
caffeinate -is tsen run     # keeps the Mac from sleeping (-s only works on AC power; doesn't prevent lid-close sleep)
```

A single `tsen run` process includes: scheduled briefs, round-the-clock anomaly monitoring, the event calendar, minute-bar collection, the
Feishu long connection (chat) and the local web UI. At startup it pushes a "started" message listing today's schedule, push channel, price
source, the LLM used by each task, Feishu sync status and the web address. Ctrl+C exits (after waiting up to 30 seconds for any in-flight
Feishu sync to finish writing).

### What gets pushed, and when

All times are local, per `timezone`.

| Push | When |
|---|---|
| Alert | Any time (checked every 60 seconds by default); only on sharp moves |
| Attribution | After the alert, as a reply under it |
| Pre-market brief | 07:30, trading days only |
| Close brief | 15 minutes after the US close |
| Weekly | Saturday 09:00 |
| Event digest | 20:00; only if "there are events tomorrow" or "something was added / rescheduled / confirmed"; the first run pushes the full calendar |
| Reminders | 5 consecutive failed checks, minute-bar collection failing for about 30 minutes, a brief / event calendar failing to generate, Feishu sync failures, monitoring scope changed |

A watchdog checks every 15 minutes: if the calendar hasn't been refreshed for 12 hours it refreshes it; after the computer wakes or the
program restarts it catches up on missed briefs (pre-market only until the open, close within 6 hours after the close, weekly within 12
hours of its scheduled time) and that evening's digest. At most one brief of each kind per day.

### Commands

```bash
tsen check                  # check config, keys, data sources, LLMs, push channel, and whether Feishu sync is on
tsen run                    # run continuously (see above)
tsen tick                   # run one check now (print only; --send pushes and stores)
tsen replay --days 5        # replay the last 5 trading days with current thresholds; --symbols LITE,night:optics:XSHG for just a few tickers
tsen brief premarket        # generate a brief: premarket / close / weekly (print only; --send to push)
tsen events                 # refresh the event calendar and generate the digest (print only; --send to push)
tsen macro                  # macro snapshot
tsen assets                 # watched assets and alert thresholds, expressed in multiples of σ
tsen scope                  # monitoring scope: holdings × themes (= tsen scope show)
tsen scope add LITE         # find linkages for a new holding, propose, replay-preview, write after confirmation (--theme picks the theme; --drop A,B / --keep C adjust candidates)
tsen scope suggest LITE     # propose only, don't write
tsen scope remove LITE      # remove a holding (the theme file is kept for later)
tsen scope undo             # undo the latest change (refuses if files were edited since; --force to override)
tsen scope check            # linkage check-up
tsen scope tune LITE        # tune alert thresholds: suggested from daily volatility, or --day 5,8,12 --rapid 60:3; replay before/after, write after confirmation
tsen scope prompt LITE      # print the context for Claude Code to prepare linkage candidates (used by the add-holding project skill)
tsen ask "LITE 今天为什么跌？"  # ask a question in the terminal (read-only preview, nothing saved); --keep uses the real database and remembers context (--keep /new clears it)
tsen web                    # open the local web UI (see below)
tsen bars                   # minute-bar store: how far each ticker is stored
tsen bars --backfill        # backfill the last 29 days without tsen run (--days N, --symbols A,B); --compact compresses old data now
tsen feishu setup           # Feishu: open the long connection, print the chat_id and your open_id
tsen feishu test            # Feishu: send a test message and reply
tsen feishu calendar-setup  # Feishu: create the event calendar and share it with you (in group chats add --open-id ou_xxx)
tsen feishu bitable-setup   # Feishu: create the alert Bitable and share it with you
tsen feishu sync            # Feishu: sync the calendar, fill in the Bitable, pull back labels now
```

Global options: `--config path` (which settings.yaml to use), `-v` (debug logging). See every option with `tsen <command> --help`.
`scope add / tune` only preview and don't write when not run in an interactive terminal; add `--yes` to write; `--replay-days N` changes
the replay length (0 = no replay).

**Manual events** (lock-up expiries, shareholder meetings, etc.): add them under `events.manual` in `settings.yaml`, for example
`- {symbol: LITE, day: 2027-01-05, kind: lockup_expiry, title: "某次增发的锁定期到期"}`.

## Local web UI

`tsen run` also starts a localhost-only web UI, by default at http://127.0.0.1:8765. It needs the `web` dependency group; if it isn't
installed, the port is taken, or `web.enabled: false`, the startup message says why and monitoring continues as usual.

| Page | What's there |
|---|---|
| Overview `/` | Two tabs on the left: **Chat** (ask directly, see "Chat") and **Feed** (every push appears live, with attributions under their alerts; while you're on Chat, the tab shows an unread count; every push has an "ask about this" button that asks with that push's full text). On the right: macro board (live snapshot, each row with a 24-hour sparkline; the Treasury yield curve with a 90-day trend), today's and tomorrow's events, today's alerts |
| Alerts `/alerts` | Filter by time range, ticker, session, rule, labelled or not; export CSV (opens directly in Excel) |
| Alert detail `/alerts/<id>` | Minute chart (up to 3 hours before to 90 minutes after, within the session; the stock, its sector benchmark and a few peers all drawn as "% vs. reference price", trigger point marked), sector / stock-specific split, macro co-movement (from the start of this move to the alert, which variables moved most unusually), the macro snapshot at the time, attribution, nearby events, earlier/later alerts in the same wave; fill in the "true cause" and notes here |
| Calendar `/calendar` | Month view and list view (14 / 30 / 60 / 100 days); filter all / macro / company / holdings; macro and company in different colors, holdings in bold, "estimated" dates in dashed boxes; click for details |
| Macro `/macro` | Trend charts for every macro variable and holding, a "who moved" ranking, a comparison view, the yield curve (see below) |

**Macro page** (all data comes from the local minute-bar store, nothing is fetched live):

- **Window**: today / 24 hours / 5 days / 1 month / custom; "在宏观页查看" (view on macro page) on an alert detail opens the window around that alert.
  When markets are closed (weekends, holidays) the preset windows end at the latest close; the page lets you switch to "up to now".
- **Trend charts**: the y-axis shows actual values (crude 104, VIX 19.4, yield 4.93%), a dashed line marks the window start, and the title
  shows the latest value and the change since the start (bp for rates, % for everything else). Time axes are aligned with a linked
  crosshair, alerts appear as markers, and periods without trading are broken rather than joined. Variables that only trade in sessions,
  like VIX and KOSPI, have their sessions joined end to end (labelled "交易时段", trading hours). Equity indices switch to futures or an
  ETF when US stocks are closed (`off_hours_symbol`). The 10- and 30-year Treasury yields only have US daytime data on Yahoo; overnight they
  are filled in from Treasury-futures moves, drawn dashed (`night_proxy: null` turns this off).
- **Who moved**: each variable's change divided by its usual volatility (a z-score), ranked, so rates, crude and VIX are comparable;
  drag-select a stretch of a chart to score just that stretch.
- **Compare**: up to 8 variables in one chart, plotted as change since the start. The y-axis can be "% / bp" (prices on the right axis,
  yields on the left, zeros aligned) or "multiples of daily volatility". Your selection is remembered and also written to the URL
  (`?cmp=wti,gold,hold.LITE`), so you can bookmark it.
- **Holdings**: holdings from `assets.yaml` form the last group and are ranked together in "who moved".
- **Fetch now** ("现在补抓"): run one round of minute-bar collection immediately.

**Other**:

- **Localhost only**: listens only on the loopback address, no login. Requests are accepted only when the Host is a local address; write
  operations must carry a random token from the page, so other websites can't call it through your browser. Setting `web.host` to any other
  address is an error. If it runs on another machine, use `ssh -L 8765:127.0.0.1:8765 that-machine` and open it locally.
- **Open on its own**: `tsen web [--port N] [--no-open]`. If `tsen run` is already running it just opens the browser; otherwise it starts a
  web-only instance: no checks, no scheduled jobs and no scheduled pushes, but questions, labels and "fetch now" from the web UI are still
  written to the real database (and `/scope` changes confirmed in the web chat are still written to the config). If another program holds the port, it tells you to pick another one.
  `tsen web --preview` uses an in-memory copy of the real database and saves nothing (questions still get answers; "fetch now" is unavailable) — click around freely.
- **Status badge** in the top bar: running · last check time / check errors / collection errors / tsen run not running (no check for over
  3 minutes); hover to see the start time, last check and minute-bar collection.
- **Install as an app**: Chrome menu "Cast, save, and share → Install page as app" (or the install icon at the right of the address bar);
  Safari menu "File → Add to Dock".
- Up/down colors default to red = up, green = down (`web.up_color: green` reverses it), and can be toggled temporarily at the top right;
  light / dark follows the system and can also be toggled manually.
- Alert charts read the local minute-bar store first and only fetch from Yahoo what isn't there; Yahoo keeps 1-minute bars for only about
  30 days, so older alerts not in the store show numbers only, without a chart.
- The feed records every push (including undelivered ones); pushes from before this table existed are filled in from the alert and brief
  records and marked "历史记录" (history).

## Chat

Two entry points, same bot and same tools behind them:

- **Feishu**: with `tsen run` running and Feishu as the push channel, message the bot in the `FEISHU_CHAT_ID` chat (@ it in a group).
  It first replies "收到，思考中…" (got it, thinking…) and then answers.
- **Local web UI**: the "Chat" tab on the overview page; works whenever `tsen run` or `tsen web` is running, no Feishu needed. When pushing
  via Feishu, the web UI and Feishu share **the same conversation** (shared context; Feishu Q&A also appears in the web UI), but Q&A in the
  web UI is not sent to Feishu. Without Feishu, the web UI has its own conversation.

For anything about the current state of things, the model first calls the 5 read-only tools below, uses only the numbers and dates they
return, and says so when it can't find something:

| Tool | Looks up | Example questions |
|---|---|---|
| `get_macro` | Macro snapshot (rates, crude, gold/silver, indices, VIX, dollar, bitcoin…) | "How are long-end yields and oil right now?" |
| `get_intraday` | Today's move (the latest trading day when closed) vs. the previous close and over the last N minutes, split into a sector part (β × benchmark) and a stock-specific part, with peers | "Why is LITE down?" "Is it the sector?" |
| `search_news` | Recent news and SEC filings (up to 10 items, 4 slots reserved for filings); holdings use preset search terms, other keywords query Google News in the language of the question | "Any recent news?" "Any new Form 4 this week?" |
| `recent_alerts` | Recently pushed alerts, their splits and the attributions at the time | "What caused that last sharp drop?" |
| `upcoming_events` | Event calendar: earnings dates (estimated / confirmed), proposed insider sales, lock-up expiries and the macro calendar | "When is the next earnings?" "What's on in the next two weeks?" |

- It knows your holdings (including each one's `note` in `assets.yaml`, where you can add recent context the model doesn't know), the push
  you "replied" to, and the last 5 turns of conversation (`chat.history_turns`).
- It understands both tickers and names: Chinese / Korean names can be partial, English names match whole words, so short tickers like ON
  or AD are looked up as tickers.
- News citations are replaced with real links by the program, and URLs the model writes itself are stripped, so no fabricated links. Chat does not search the web.
- It only answers questions: it can't set reminders or place orders; on buy/sell questions it gives an analytical framework, not instructions.

**Commands that skip the LLM** (answered in seconds):

- `/new` (or `/reset`, "新对话"): start a new conversation.
- `/macro` (or `/m`, "宏观", "宏观数据"): a macro snapshot.
- `/scope` (or "监控范围"): show the current monitoring scope.
- `/scope add <ticker> [theme]`, `/scope suggest <ticker>` (propose only), `/scope remove <ticker>`, `/scope undo`, `/scope check`,
  `/scope tune <ticker> [全天 5 8 12] [急涨 60:3]`: the same as `tsen scope` on the command line. For anything that changes config it first
  replies with a proposal; answer "确认" (or 确定 / 是 / 好 / yes) to write it, "取消" (or 算了 / 不 / no) to drop it, or "去掉 X" / "加上 X"
  (remove / add X) to adjust candidates first; valid for 30 minutes. Takes effect immediately after confirmation, no restart.

To test the same logic in a terminal: `tsen ask "question"` copies the real database into memory, refreshes the event calendar once and
answers, saving nothing; `tsen ask --keep "question"` uses the real database and records into a "terminal" conversation, so you can keep
asking follow-ups.

## Monitoring rules and sensitivity

### Which assets to watch: `config/assets.yaml`

```yaml
defaults:                       # default thresholds per asset class; any asset can override them in its own alert
  us_equity: {hours: 24x5, rapid_pct: {5: 1.5, 15: 2.5, 30: 3, 60: 3}, z: 4.0, day_pct: [5, 8, 12]}
  future:    {rapid_pct: {5: 0.6, 15: 1.0, 30: 1.4, 60: 1.4}, z: 4.0, day_pct: [1.5, 2.5, 4]}   # ±2% in a day is already a big move for gold
assets:
  - {symbol: LITE, name: Lumentum, class: us_equity, theme: optics, queries: {en: ["Lumentum"], zh: ["Lumentum 光模块"]}}
  # - {symbol: "GC=F", name: 黄金, class: future}
```

- Asset class `class`: `us_equity` (US stocks / ADRs), `foreign_equity` (foreign stocks), `future` (CME futures), `crypto`.
  ADRs can set `underlying` (the primary listing), `adr_ratio`, `fx_symbol`. `holding: false` marks a watch-only asset that isn't a holding.
- US stock hours `hours`: `24x5` (the example's default: adds the 20:00–04:00 ET overnight session, Sunday night through Friday) | `extended`
  (04:00–20:00: pre-market + regular + after-hours; the default if you delete that line from defaults) | `regular` (regular hours only).
  With `sources.night.provider: none`, 24x5 behaves like extended.

| Asset | Sessions | Reference price |
|---|---|---|
| US stocks | Overnight 20:00–04:00 (Hyperliquid), pre-market 04:00–open, regular, after-hours close–20:00 (ET); not watched from Friday 20:00 to Sunday 20:00 | After-hours = today's close; overnight, pre-market, regular = previous trading day's close |
| Futures | CME: 18:00 ET the previous day to 17:00 that day | Price at 17:00 at the end of the previous session |
| Crypto | UTC calendar day | UTC midnight |
| Foreign stocks | The local exchange's regular hours (including lunch breaks) | Local previous close |

### Two rules

All magnitudes are in percentage points of the reference price ("+2% falling to -1%" is 3 points):

- **Rapid move** `rapid_pct`: {window minutes: minimum %}. The drop from the **high** of the last that-many minutes to the current price
  (or the rise from the low) reaches this size, and the z-score ≥ `z` (unusual relative to the stock's own last-5-day volatility, so it
  tightens automatically on volatile days). Using the high/low rather than the window start catches "spike up, then fall back below
  water". Smaller numbers are more sensitive.
- **Day cumulative** `day_pct`: measured from the higher of the reference price and today's high (including earlier sessions that share the
  same reference price), a drop of this size (symmetric for rises) pushes once per level, and resets after a new high / low. This covers
  opening gaps and slow multi-hour slides.

There is also a "stock-specific" rule (abnormal return after removing the sector), off by default.

- No rapid-move checks in the first 10 minutes of each session (the opening auction is noisy; gaps are left to the day-cumulative rule);
  after-hours is the exception, since earnings often come out at 16:05 and those first minutes matter most. The session after a lunch break also warms up first.
- Pre-market, after-hours and overnight trading is thin with stray bad prints, so the median of the last 3 bars is used: a single bad print
  can't trigger, and real moves are only 1–2 minutes late.
- No repeats for the same wave: one push per direction within 15 minutes (or the window length), with another "扩大" (widened) push only if
  the move doubles; a day-cumulative level isn't pushed separately if a rapid-move alert for the same wave just went out. Sessions with the same
  reference price form one chain (Monday after-hours, Tuesday overnight, pre-market and regular all refer to Monday's close), so after a
  "down more than 5%" push after hours, it won't be pushed again overnight or the next morning.
- Several names in the same theme moving the same way: merged into one push with one attribution; names that follow within 10 minutes are
  threaded under the first as replies. Assets without a theme are not merged.
- Failed pushes are retried for 30 minutes (title marked "补发", resent). After a restart the cooldown state is restored from the database, so nothing is pushed twice.

### Sector linkage: `config/themes/`

"Adding a stock" is easy; the hard part is the circle of things that move with it. These are written per sector as "themes", one file each
(the file name is the theme name), and a holding points to one with `theme:`. **A theme no holding references is inactive** (no data
fetched, no events collected, no pushes), so you can keep spares around; sell the last holding and the whole circle stops automatically.

```yaml
# config/themes/optics.yaml (referenced by LITE in the example)
name: 光模块
focus: 数据中心光模块与光器件（800G / 1.6T、CPO、硅光）     # goes into prompts
benchmark: basket                 # sector benchmark: an ETF / index ticker, or basket (equal-weight basket of the US names in peers)
peers: {COHR: Coherent, AAOI: Applied Optoelectronics, CIEN: Ciena, FN: Fabrinet, GLW: 康宁, VIAV: Viavi}   # move together
overnight: {"300308.SZ": 中际旭创, "300502.SZ": 新易盛, "300394.SZ": 天孚通信}   # overnight signals: automatically become watch-only assets
overnight_alert: {rapid_pct: {5: 2.5, 15: 4, 30: 5, 60: 5}, day_pct: [5, 8, 12]}  # thresholds for the overnight basket
catalysts: {NVDA: 英伟达, ANET: Arista, AVGO: 博通, MSFT: 微软}  # big customers / suppliers: event calendar and attribution only
news: {en: ["optical transceiver"], zh: ["光模块"]}          # sector news queries
indicators:                       # sector indicators: attached only to this sector's alerts
  - {key: cny, name: 美元/人民币, symbol: "CNY=X", kind: level, ref: 24h}
```

The four kinds of linkage are kept separate: names that move together go in `peers`, used for the sector / stock-specific split and the
co-movement list; big customers that move the sector but don't usually move with it go in `catalysts` (after removing the market, NVIDIA's
daily return correlation with LITE is only 0.29, and putting it in peers would skew the split). When an exchange has two or more overnight
signals, they are combined into an equal-weight basket that triggers once per wave; a single name is pushed on its own only if it moves
≥ 3% itself and deviates from the basket by as much (`overnight_single_pct`; `overnight_basket: false` pushes each separately).

**If you'd rather not write it by hand**: `tsen scope add <ticker>` (Feishu `/scope add <ticker>`) finds candidates for you (Yahoo similar
stocks and industry leaders, Finnhub, existing themes), scores each on daily data (peers and benchmark over the last 120 trading days,
overnight signals over the last 160; peers: residual correlation after removing SPY ≥ 0.5; benchmark: the higher R² of the industry ETF and
the peer basket; overnight signals: partial correlation of the foreign stock's same-day move with the holding's next-day opening gap ≥ 0.3),
scales alert thresholds to its daily volatility, and merges it into an existing theme if the linkage is strong enough. Before writing it
replays a few days with the suggested thresholds to tell you roughly how many pushes to expect; it backs up to `data/scope_history/` first,
and `tsen scope undo` reverts.

"Nominating" peers, foreign counterparts and big customers relies on the model's own knowledge, which the local model isn't up to, so by
default it's handed to **Claude Code** (using your subscription, no API calls): open Claude Code in this project and say "add a holding LITE";
the `add-holding` project skill (`.claude/skills/`) verifies tickers online, writes `data/scope_candidates/LITE.json`, then runs
`tsen scope add` to build a proposal, which is only written after you confirm. Without prepared candidates, only the other sources are used.
To let the program call Claude online itself, set `llm.tasks.scope` to `[claude_research]` and fill `ANTHROPIC_API_KEY`.

### Tuning sensitivity

1. `tsen assets`: each asset's thresholds expressed as "this many times its recent volatility (σ)". The same 1.5% in 5 minutes is a normal
   threshold for a single stock and practically never fires for gold.
2. `tsen replay --days 10`: replay the last 10 trading days (including pre-market, after-hours, overnight and foreign sessions) with the
   current thresholds to see how many pushes you'd get and when.
3. `tsen scope tune <ticker>`: suggests thresholds from the last 120 trading days of daily volatility (the defaults are set for a stock with
   5% daily volatility, futures for 2%), or give numbers directly (`--day 5,8,12 --rapid 60:3`; in Feishu, "全天 5 8 12 急涨 60:3"; only the
   windows you write are changed, `60:0` removes that window). It replays "before / after", and after confirmation writes to the right place
   (holdings into `assets.yaml`, overnight baskets into the theme's `overnight_alert`). Pure computation, no LLM.
4. Linkages shift with market regimes: the "linkage check-up" at the end of the weekly brief appears only when peers / overnight signals have
   clearly weakened or a strong new candidate shows up; `tsen scope check` any time. Suggestions only; nothing is changed automatically.

The full detection design (why it's computed this way, measured numbers) is under "关键设计决策" (key design decisions) in CLAUDE.md.

## Macro data

Every alert push ends with a macro snapshot, which the attribution model also sees. View it any time: send `/macro` in Feishu or the web UI,
or run `tsen macro` in a terminal. Add or remove variables in `macro.indicators`:

| Variable | Data | Change measured as |
|---|---|---|
| US 10-year / 30-year | Yield indices `^TNX` / `^TYX`, about 15 minutes delayed | vs. previous close, bp |
| US 2-year, 2s10s spread | US Treasury daily yield curve (official) | — |
| WTI crude, gold, silver | CME continuous contracts `CL=F` / `GC=F` / `SI=F`, about 10 minutes delayed | vs. 24 hours ago |
| S&P 500, Nasdaq | `^GSPC` / `^IXIC`; futures `ES=F` / `NQ=F` when US stocks are closed | vs. previous close; futures vs. the US close |
| VIX, dollar index, USD/JPY, bitcoin | `^VIX`, `DX-Y.NYB`, `JPY=X`, `BTC-USD` (bitcoin isn't attached to alert pushes) | VIX vs. previous close, the rest vs. 24 hours ago |

- Fields per item: `key`, `name`, `symbol`, `group`, `kind` (`yield` | `price` | `level`), `ref` (`close` vs. the last US close | `24h`),
  `off_hours_symbol` / `off_hours_name` (the future or ETF used when US stocks are closed, e.g. Philadelphia Semiconductor `^SOX` → `SOXX`),
  `in_alert` (whether it's attached to alert pushes), `night_proxy` (which Treasury future fills yields overnight, default `auto`).
- Switches: `macro.attach_to_alerts`, `timeout_seconds` (waits at most 10 seconds when pushing; omitted if unavailable), `cache_seconds` (60), `treasury_curve`.
- Changes are computed from minute bars only, never daily bars: around futures rolls the daily and minute series are different contracts,
  and daily bars would show fake big moves. The snapshot is stored with the alert (`alerts.macro_json`).
- Indicators tied to a particular sector (e.g. USD/CNY and the ChiNext index for optical modules) go in the theme's `indicators`; they're
  attached only to that sector's alerts and listed separately as "板块指标" (sector indicators) in `/macro`.

## What the event calendar collects

Add or remove items under `events` in `settings.yaml`:

- **Companies**: holdings, their foreign primary listings, and the `peers` and `catalysts` of active themes (in the example: optical-module
  peers, NVIDIA, Arista, Broadcom, cloud providers…). Companies unrelated to any theme that you still want go in `events.related`. Sources:
  - Earnings dates: yfinance (all tickers, mostly estimates), Japan Exchange Group's "決算発表予定日" (earnings announcement schedule; Tokyo
    listings, official), SEC 6-K (results release / call times announced by foreign issuers), Finnhub (with a key);
  - Insider proposed sales: SEC Form 144 (holdings only, ≥ $1 million, `insider_sale_min_usd`);
  - Manual entries: `events.manual` (lock-up expiries, shareholder meetings, etc.).
- **Macro** (`events.macro`, all from official schedules, no keys needed):

  | Key | Contents | Source |
  |---|---|---|
  | `fed` | `fomc` rate decision + press conference (meetings with a dot plot are marked), `minutes`, `chair` speeches and congressional testimony; optionally `beige_book` | Federal Reserve |
  | `us_data` | `cpi` `ppi` `jobs` (payrolls) `jolts`: BLS, needs `BLS_USER_AGENT`; `pce` `gdp`: BEA; `retail_sales`: Census Bureau; optionally `eci`, `durable_goods` | Each agency's release schedule |
  | `treasury_auctions` | Long-end Treasury auctions, default `[10Y, 20Y, 30Y]` | US Treasury |
  | `boj` | Bank of Japan policy meetings | Bank of Japan |
  | `korea_exports` | Korea monthly exports and first-20-days exports | Derived from convention, marked "estimated" |
  | `opex` | US monthly options expiration | Derived from the exchange calendar |
  | `us_market` | US market holidays and early closes | Exchange calendar |

- Nightly digest: tomorrow's events + what was added / rescheduled / confirmed since last time + the next 14 days (macro and company listed
  separately). For estimated dates only changes within 45 days are reported (far-out estimates change often and would be noise); macro events
  are scheduled far in advance, so "new" ones aren't announced individually, only reschedules.
- For attribution, the model sees events in the 24 hours before the move (e.g. CPI released pre-market, a peer reporting last night) and in the next 24 hours.
- It collects 100 days ahead (`events.lookahead_days`); quarterly earnings are about 91 days apart, so every company's next report is in the database.

## Data and storage

| Content | Source | Cost |
|---|---|---|
| Minute and daily bars (primary, foreign) | Yahoo Finance (yfinance) | Free, unofficial API; 1-minute bars kept for only about 30 days |
| Price fallback, official daily closes | Alpaca (real-time IEX / SIP older than 15 minutes) | Free account (optional) |
| US overnight session (20:00–04:00 ET) | trade.xyz stock perpetuals on Hyperliquid | Free public API, no key; read-only market data, this project doesn't trade |
| US Treasury yield curve | US Treasury | Free, official |
| Company news, earnings calendar | Finnhub | Free key (optional) |
| English / Korean / Chinese news | Google News RSS | Free |
| US filings, Form 144, 6-K | SEC EDGAR | Free, requires a contact email |
| Earnings dates | yfinance, Japan Exchange Group | Free |
| Macro calendar | Federal Reserve, BLS, BEA, Census Bureau, US Treasury, Bank of Japan; options expiration and holidays derived from exchange calendars | Free |
| Briefs, attribution, event digest, chat | Local LM Studio (default) / Claude / OpenAI | Local is free; cloud is billed by usage |

**What's in `data/`** (the whole directory is excluded from git):

- `tickersentinel.sqlite3`: the main database. Alerts and attributions (`alerts`, also an event-study dataset, with `label` / `notes` columns
  for labelling afterwards), the event calendar, briefs, push records (`messages`), chats, Feishu sync mappings.
- `bars.sqlite3`: the minute-bar store (see below). The `-wal` / `-shm` files next to both databases are SQLite working files.
- `outbox.log`: push contents when the channel actually in use is the terminal.
- `scope_history/`: backups taken before `tsen scope` changes; `scope_candidates/`: linkage candidates prepared by Claude Code.

**Local minute-bar store** (`storage.bars_path`):

- What's stored: base macro variables and the sector indicators of active themes, plus holdings, benchmarks, peers and overnight signals.
  When the monitoring scope changes, new tickers start being stored automatically.
- How: `tsen run` collects incrementally every 120 seconds (`bars.collect_seconds`); new tickers are backfilled for the last 29 days in the
  background (`bars.backfill_days`). Yahoo during the day, Hyperliquid for the US overnight session. The Treasury yield curve is fetched every
  12 hours and kept for 2 years (`bars.treasury_years`). 1-minute bars older than 120 days (`bars.keep_minute_days`) are compressed daily into
  5-minute bars and kept indefinitely. Pure code, no LLM, and the web UI need not be open.
- Size: the author's store was about 41 MB after a 29-day backfill plus a week of running.
- `bars.enabled: false` turns collection off.

**When offline, rate-limited, or the computer sleeps**: a single data source failing never stops the whole thing; higher layers degrade
automatically (prices switch to the fallback, the macro snapshot is omitted if unavailable, the calendar keeps its last result). Tickers that
fail during minute-bar collection are re-fetched from where they broke off in the next round and catch up once the source recovers; the same
goes for a stopped `tsen run`, which fills the gap on its next run (up to 29 days). Moves during sleep can't be detected after the fact;
checks resume on wake, and the watchdog catches up on missed briefs and digests. Without `tsen run`, data isn't updated automatically —
use `tsen bars --backfill` or "fetch now" in the web UI.

## Long-term running

- **Runs for days on end**: at startup it raises the open-file limit from macOS's default 256 to 10240; the per-minute checks, minute-bar
  collection and the watchdog all have time limits, so a hung request only abandons that round; consecutive failures trigger reminders
  (see "What gets pushed, and when").
- **After updating the code**: restart `tsen run` after `git pull` (code doesn't hot-reload; the web UI's static files are versioned, so a
  page refresh gets the new ones). On restart the cooldown state is restored from the database, so alerts already pushed today aren't
  repeated; if dependencies changed, run `uv pip install -e ".[dev,web,feishu]"` again first.
- **Auto-start at login on a Mac** (optional; below is a launchd example — replace the paths with yours, put it under
  `~/Library/LaunchAgents/`, and load it with `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/tickersentinel.plist`):

  ```xml
  <?xml version="1.0" encoding="UTF-8"?>
  <!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
  <plist version="1.0">
  <dict>
    <key>Label</key><string>tickersentinel</string>
    <key>ProgramArguments</key>
    <array>
      <string>/usr/bin/caffeinate</string><string>-is</string>
      <string>/path/to/tickersentinel/.venv/bin/tsen</string><string>run</string>
    </array>
    <key>WorkingDirectory</key><string>/path/to/tickersentinel</string>
    <key>RunAtLoad</key><true/>
    <key>KeepAlive</key><true/>
    <key>StandardErrorPath</key><string>/path/to/tickersentinel/data/tsen.log</string>
  </dict>
  </plist>
  ```

- **Deploying to another machine** (a VPS or a small home server): there's no local LLM there, so set `llm.tasks` to `[anthropic]` or
  `[openai]` (and fill the matching key), or point `llm.providers.local.base_url` at a reachable service and delete the `lmstudio` block.
  View the web UI through SSH port forwarding. Supervise it with systemd:

  ```ini
  # /etc/systemd/system/tickersentinel.service
  [Unit]
  Description=tickersentinel
  After=network-online.target

  [Service]
  WorkingDirectory=/opt/tickersentinel
  ExecStart=/opt/tickersentinel/.venv/bin/tsen run
  Restart=always
  RestartSec=30

  [Install]
  WantedBy=multi-user.target
  ```

## Development

```bash
uv pip install -e ".[dev,feishu,web]"   # without feishu / web installed, the related test files are skipped entirely
.venv/bin/pytest -q                     # runs fully offline, no network or keys needed
```

Tests use synthetic market data and fake data sources and read `tests/fixtures/config/` (a frozen config, independent of the example config).

(macOS). yfinance is pinned to 1.x (`>=1.7,<2`) because the program uses a few of its internal APIs to tell "fetch failed" apart from
"market closed".
